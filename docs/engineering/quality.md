# 基础工程质量规范

架构和职责边界见 [架构](architecture.md)，执行流程见 [开发流程](development.md)。本文件维护通用代码、配置和可复现要求。

## 代码与命名

- 一个模块有一个清晰变化原因，使用业务语言命名聚合、用例、端口、组件和错误。
- TypeScript 启用 `strict`，边界输入先解析为 `unknown` 再验证，不用 `any` 绕过契约；Go 显式处理错误。
- 领域错误与应用错误保持稳定分类；禁止依赖数据库原始错误字符串或用户文案判断业务分支。
- 避免重复维护同一规则、权限矩阵、错误码或评估算法。前端做反馈，后端执行最终业务校验。
- 函数和组件按职责拆分，生产、测试及脚本代码文件上限 700 行；接近上限时优先按职责拆分，不以拆碎无意义文件规避检查。
- 不为了未来可能复用引入抽象基类、通用 CRUD 框架、泛化规则 DSL 或服务定位器。
- 注释解释约束与原因，不能替代正确命名；不留无归属 TODO 或失效示例。

## 输入、错误与资源

- HTTP 边界限制 body 大小，校验 JSON 对象与必填字段，明确拒绝非法环境、规则、百分比和 revision。
- 明确区分非法输入、未登录、无权限、不存在、业务冲突与内部错误。
- 预期冲突不产生部分写入；内部错误不暴露 SQL、堆栈、文件路径或密钥。
- 后端统一 request context、请求/数据库超时和优雅关闭；取消请求不继续执行无主写入。
- 时间以 UTC 保存并通过带时区 ISO 8601 输出，界面按用户时区展示。
- ID、时钟及不可确定外部能力通过端口注入，测试使用确定性实现。

## 数据库与配置

- 使用参数化 SQL；分页有上限，排序有确定性次序。
- migration 版本化、可从空库运行；重复执行迁移入口不重复 seed 或破坏现有数据。
- 同一环境 Key 唯一、同一 Flag 优先级唯一必须有数据库约束。
- 当前配置、完整版本和审计同事务提交；变更接口均校验 expected revision。
- `.env.example` 只包含说明与无敏感性的示例；配置启动时校验，缺少关键配置给出明确反馈。
- 不写死开发者绝对路径、部署域名、生产密码或本机端口；临时端口由测试配置管理。

## 依赖与构建

版本策略由 [技术栈](tech-stack.md) 维护。提交锁文件，构建不临时下载未固定的工具；任何依赖、架构检查或质量门禁的变更均注明原因和验证。

API DTO 与数据库模型分别维护；未来契约文档、生成物和脚本必须来自明确源文件及可重复生成命令，不能人工维护两份近似事实。

## 门禁与报告

实施阶段建立格式、lint、类型、架构边界、文件规模、文档链接、测试与构建检查。具体可执行入口由 [测试执行手册](../testing/TESTING_RUNBOOK.md) 维护，尚未实现的检查不能作为当前证据。

局部开发先运行最窄有效检查，提交/交付运行受影响的必要门禁。完整套件通过后，在相关实现未变化时不为形式重复执行；失败必须定位原因，不能禁用门禁或删除断言来掩盖问题。

生成报告和截图放入 `test-results/` 等忽略目录，敏感运行数据不得提交。提交源代码、配置模板、迁移、必要测试、规范、验证摘要与可复现脚本。
