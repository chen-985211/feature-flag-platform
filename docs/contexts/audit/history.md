# 操作历史与原子审计

Audit 拥有追加式操作历史，不拥有配置求值或版本恢复；回滚读取 Flags 的版本快照。日志、版本与审计是三种不同资料，不能互相替代。

## 必须记录

- 创建 Flag、修改基本信息、启用/停用。
- 添加、修改、删除属性和百分比规则。
- 调整顺序、复制、发布与回滚。

每条记录至少包含 ID、目标 Flag ID、目标环境/Key、动作类型、真实 Actor ID 与可显示名称、UTC 时间、目标新 revision、必要变更摘要与 request ID。复制/发布包含源 Flag、环境与 revision；回滚包含被恢复的 revision。

摘要保存理解变更所需的结构化字段及前后差异，界面根据动作类型展示文字；不能只保存无法稳定解析的自然语言字符串。

界面的摘要从已有结构化记录读取，不回写数据库。默认说明具体动作与版本，展开对比仅展示变化的业务字段及规则；完整原始记录可另行展开和复制。解析不兼容的记录保留原始数据并明确提示，不能以当前配置猜测历史。复制/发布时规则 ID 的重新分配不当作规则条件变化。

## 原子性与边界

Flags 调用方通过应用层 AuditAppendPort 进入 Audit 公开用例，基础设施把配置仓储、版本仓储和审计写入绑定到同一 PostgreSQL 事务。

审计写入失败必须使业务变更及版本一起回滚。禁止配置先提交再通过异步事件、队列或另一个事务补写审计。

未成功的权限/校验/冲突请求不产生“成功修改”记录；可以在诊断日志中记录稳定错误，但不可伪造成功历史。评估、列表和历史查看均不生成配置操作记录。

历史只追加，不向普通用户提供修改或删除入口。分页按时间与 ID 确定性排序。操作者名称可以保存当时快照，身份仍通过 Actor ID 关联，不能由请求伪造。

## 敏感信息

不保存登录密码、会话/CSRF token、数据库 URL、部署密钥或完整评估用户属性。摘要必须有大小限制和明确字段，避免把未经筛选的 HTTP body 整体写入。

## 验证

unit 测试覆盖动作摘要与输入契约。真实数据库 integration 测试覆盖写入成功、历史排序和写入失败时配置/版本/历史共同回滚。API 契约验证只读权限和 Actor 来源。
