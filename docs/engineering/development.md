# SDD + TDD 开发流程

## 地位与当前任务

SDD 指 Spec-Driven Development（规格驱动开发），TDD 指 Test-Driven Development。架构见 [架构](architecture.md)，测试细节见 [测试策略](../testing/TESTING_STRATEGY.md)。

当前用户授权先建立规范文档。本次为纯文档 Small 任务，不据此开始业务代码、测试框架或部署的实现。后续完整平台开发属于 Large。

## 任务分级

按影响和风险分级，不按改动行数、预计耗时或文件数量分级。

| 等级  | 判定                                                   | 示例                                                                                       | 流程                                                |
| ----- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| Small | 局部、可逆、低风险，不改变领域语义、公开契约或架构边界 | 间距、颜色、排版、普通文案、非语义布局、文档、格式；已有契约内的局部交互修复               | 简短说明 → 直接修改 → 目标验证                      |
| Large | 新能力、核心流程、业务规则、契约、持久化或结构变化     | 评估规则、灰度、授权、会话、版本/事务、API/schema、迁移、跨上下文端口、发布/回滚、核心重构 | Spec → 需求确认 → Plan → 方案/执行确认 → TDD → 验收 |

“改 UI”不自动等于 Small：如果修改状态含义、发布动作、权限语义、保存流程或核心导航，应按 Large。单行权限或数据库修改也属于 Large。

## 开工说明

会修改项目状态的连续任务开始时，简短说明：目标范围、Small/Large 与原因、实际命中的规则文档、涉及上下文/层级、最低有效验证。已读且未变化的文档注明复用，不要求每回合重新阅读。

只读分析不要求完整开工说明。执行中新增边界、契约或风险时先补充路由和分级；不能用最初的 Small 分类覆盖新增 Large 范围。

## 小任务流程

1. 读取路由命中的相关规则并说明目标。
2. 直接完成最小必要修改，不强制新建 Spec/Plan，也不额外等待用户确认。
3. 纯视觉调整使用真实浏览器渲染检查；有局部行为变化则在最低有效层执行 TDD。
4. 运行相关检查，汇报变更与验证结果。

纯文档、注释、格式、可逆视觉细节不要求编造自动化测试。构建或测试配置通过真实配置检查、构建或受影响套件验证，不为配置写镜像实现的测试。

## 大任务流程

### Spec

先保存 [Spec 模板](../templates/spec.md) 所要求的背景、范围、统一语言、上下文、状态 owner、领域不变量、外部行为、边界情况、验收编号、风险和待决策项。Spec 表达需求与验收，不混入逐文件实施步骤。

验收必须可判定，例如“版本冲突后数据库中配置、版本与历史均无新增写入”，不能只写“支持乐观锁”。需求记录应区分已确认决定和待确认细节。

### 确认与授权

需求与方案确认可以来自本次或已有对话、已确认的 Spec/Plan，以及用户明确的执行授权。已经确认的范围、技术选择和规则必须复用，不重复请求相同确认。

只请求尚未确定、会改变交付范围或核心语义的决策。用户已明确授权按确定方案端到端实施时，可在该授权范围内先补齐 Spec/Plan 并继续；每个 TDD 步骤不需要重新审批。用户明确要求“先确定方案/先生成文档”时，则只完成该阶段。

### Plan

基于确定的 Spec 保存 [Plan 模板](../templates/plan.md)：职责与路径、聚合/用例/端口/适配器、依赖方向、数据与事务、API、分步实施、每步 Red 测试及回归层级、迁移与风险。

Spec/Plan 必须先于对应业务实现完成并可审查。不能用事后补写文档掩盖直接编码；不能把一个尚未确定的大任务拆成多个 Small 来规避 SDD。

### TDD 与验收

1. Red：先写一个表达验收行为的测试，实际运行并确认因目标行为缺失而失败。
2. Green：实现满足该行为的最小代码，不附带增加范围。
3. Refactor：在测试保护下整理职责与重复，再运行相关检查。
4. 对下一个验收点重复以上步骤。
5. 运行与影响相符的最终门禁，记录验收编号、测试层级、结果与剩余风险。

若 Red 因环境、导入配置或语法错误失败，先修正测试基础设施；这不算有效的行为 Red。已有行为重构可先添加表征测试，再在保护下重构，不能故意破坏代码制造失败。

## 实施顺序与事实归属

业务需求 → DDD 规则和状态 owner → Clean 用例及端口 → 领域/用例 Red → 最小实现 → 真实适配器及契约 → 组件 → 少量 E2E。

不同入口的同一业务动作必须共用规则 owner 与结果契约。先确定最终后置条件和输入维度，再修具体案例；已有缺陷样本应与其所属不变量一起被回归测试覆盖。

需要可行性验证的新库、迁移、事务或部署能力，在相关 Plan 中记录验证结果。选择成熟方法时优先读取现有项目事实或官方资料，不以记忆猜测版本行为。

## 完成与记录

完成条件由 [测试要求](../testing/TESTING_REQUIREMENTS.md) 与 [交付验收](../delivery/acceptance.md) 定义。通过结果绑定对应代码和配置；它们未变化时可复用，发生相关变化后才重新运行。

最终说明包含修改结果、上下文与层级、测试新增/运行/未运行、未覆盖风险；纯文档任务说明文档检查即可。过程记录按 [AI 记录约定](../ai/README.md) 保存，不能编造测试、部署、覆盖率或 TDD 证据。
