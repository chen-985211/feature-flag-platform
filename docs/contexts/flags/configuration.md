# 配置、版本、排序与环境流转

## 聚合与数据

一个 Flag 聚合拥有 ID、名称、Key、环境、启用状态、默认值、稳定 seed、revision、规则集合与创建/更新时间。环境在创建后固定；Key 可以通过基本编辑修改，但必须遵守目标环境唯一约束。

每条规则拥有 ID、类型、priority、配置和命中返回值。属性规则使用 attribute/operator/expected，百分比规则使用比例；不强制把第三类规则伪装成 equals/in。

PostgreSQL 规划使用 `flags`、`rules`、`flag_versions`；用户/会话和审计属于其他上下文。完整 schema、字段长度与索引由数据库任务 Spec/Plan 定义。

数据库必须保证 `(environment, key)` 唯一、`(flag_id, priority)` 唯一、规则外键有效、合法环境和比例范围。业务校验提供清晰反馈，数据库约束处理并发下的最后冲突。

## 统一提交

所有配置写入由统一提交用例/策略协调，而不是各 handler 分别维护版本与历史。

1. 从可信会话取得 Actor，并校验目标环境权限。
2. 在事务内锁定目标当前状态并比较 expected revision。
3. 加载聚合，执行领域修改并校验规则与优先级。
4. 更新关系表，将 revision 加一，保存完整不可变配置快照。
5. 经 Audit 公开用例在同一事务写入操作历史。
6. 提交后返回新 revision 和权威配置。

创建没有旧 revision，使用唯一约束处理并发创建；成功创建从 revision 1 开始并生成初始版本和审计。其他所有配置变更均提交 expected revision，包括基本信息、启停、规则增删改、排序、发布和回滚。

revision 不匹配、校验失败、唯一冲突、权限失败或审计失败均不得留下部分配置、版本或历史。冲突是明确业务错误，不静默覆盖，也不自动重试旧写入。

## 版本与回滚

版本快照包含名称、Key、启用、默认值、seed、完整规则及顺序，带 snapshot schema version、revision、时间与操作者。Flag ID、环境和创建时间是目标聚合身份，不随回滚跨环境移动。

历史版本不可修改。回滚以选定快照内容形成一个新的 revision，保留旧版本；回滚也受权限、乐观锁及 Key 唯一约束保护。恢复历史 Key 发生冲突时返回明确错误，配置保持原状。

当前 revision 与其快照必须一致。评估用一次数据库查询取得完整当前快照，不能分别读取基本信息和规则后拼接不同提交版本。

版本差异按稳定字段呈现，规则比较包括顺序、条件和返回值；不把数据库行顺序、更新时间等技术噪声当作配置差异。

## 规则排序

priority 为正整数，数字越小越先执行，单个 Flag 内拒绝重复。删除规则不要求剩余编号连续，显示顺序必须确定。

排序提交完整规则 ID 序列与 expected revision。序列必须恰好覆盖当前规则，不允许重复、缺失、外部 Flag 的 ID 或额外 ID。提交后按顺序重新分配 1～N。

唯一约束可延迟至事务提交检查，或采用经过集成验证的等价事务内更新策略；不能通过取消数据库唯一约束解决临时冲突。排序的关系更新、版本和历史一次提交。

## 复制

复制选定的源版本，在另一个环境创建新 Flag。复制名称、Key、启停、默认值、规则和 seed，为目标 Flag 与规则分配新 ID，目标 revision 从 1 开始。

目标已有相同 Key 则返回冲突；复制不承担覆盖行为。来源版本不可变，所以源后续编辑不改变本次已选内容。历史记录来源 Flag/环境/revision 和目标环境。

## 发布

发布选定源版本到相同 Key 的已有目标环境配置。目标不存在时提示先复制，不隐式创建。禁止来源与目标为同一 Flag。

操作前返回差异预览、明确源 revision 与目标 expected revision；目标发生变化后，旧预览不得直接覆盖。真正发布时重新校验权限、源快照、目标身份和 revision。

发布保留目标 Flag ID、Key、环境和创建时间，应用源名称、启停、默认值、seed 与规则。源规则映射为目标自身规则 ID，不引用其他 Flag 内部实体。目标产生新版本与自己的审计，不搬运源历史。

发布到 production 以及 production 的其他修改均遵守 [权限规范](../identity/access-control.md)。

## 核心验证

单元测试证明聚合不变量、优先级、版本冲突策略和快照恢复；真实 PostgreSQL 集成证明唯一约束、排序更新、并发写入、完整回滚以及配置/版本/审计的原子一致。

事务失败注入必须通过真实写入边界模拟，例如让审计插入被约束拒绝，随后读取确认三类数据均未变化；只验证 mock 调用次数不足以证明原子性。
